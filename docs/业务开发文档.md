### 当前代码状态，避免误解

- 通用数据库 CRUD 已保留在 ServiceImpl 和 Mapper 中，直接复用。
- 按学习骨架的既定要求，所有 Controller 方法体仍是 `return null;`。这只是接口占位；实现对应 Redis 功能时顺手接通调用即可，**不把接 Controller 或 CRUD 接线作为独立学习阶段**。

### 开始练习前只需确认这些条件

Java 17；默认数据库 `epic_learning`，SQL 目标为 MySQL 5.7.19+。MySQL 5.7 不执行表定义中的 `CHECK` 约束；Redis 练习使用 6.2+。初始化与启动步骤直接参照项目 README，不作为本课题。

Swagger 地址：`http://localhost:8080/swagger-ui/index.html`。

登录校验不设配置开关，两个拦截器已在 `WebMvcConfiguration.addInterceptors` 中注册并直接生效。Redisson 随应用启动创建，无额外启用开关；启动前需确保 `RedisConfiguration` 中的连接参数正确且 Redis 可连接。StringRedisTemplate 使用 `application.yml` 中的 Redis 连接配置。工具类与后台任务当前未全部注册为 Bean，完成实现后再配置注入和调度。

### 贯穿 Redis 实现的业务约束

现有数据库和容量校验已经提供基础保护，Redis 设计必须尊重这些规则：

- 用户预约某站点某时段的名额，不指定充电桩。
- 名额上限由桩数与可分配功率共同限制；Redis 预占不可突破 quota。
- MySQL 的 `reserved` 统计 SUCCESS 订单，PROCESSING 预占需要另行识别。
- 同用户同 requestId 是请求重试；不同 requestId 不代表可以重复占同一时段。
- `(user_id,request_id)` 和 `(slot_id,active_user_id)` 唯一约束已经存在。
- PROCESSING 可以进入 SUCCESS、FAILED 或 CANCELLED；已取消订单不能被迟到消息复活。
- Redis 是缓存和并发协调工具，数据库仍需要提供最终的唯一性、事务和容量保护。

## 第一阶段：邮箱验证码登录与鉴权

> 难度：★★★☆☆｜涉及：Redis String、Hash、TTL、拦截器、ThreadLocal。

### 1. Mapper 与 DTO

使用现有 `UserMapper.findByEmail/findById/insert`、`EmailCodeDTO`、`LoginDTO` 和 `LoginVO`。
没有密码字段，本阶段不要添加 MD5 登录或改成 HttpSession。

### 2. UserServiceImpl

| 方法 | 要实现的业务 |
| --- | --- |
| `sendCode(dto)` | 邮箱规范化、生成随机验证码、Redis 保存、有效期、发送冷却 |
| `login(dto)` | 校验并一次性消费验证码、查询或注册用户、生成 Token、保存 Hash 登录态 |
| `logout(authorization)` | 删除当前 Token 登录态，使后续访问失效 |
| `current()` | 已有查询；依赖拦截器正确设置当前用户 ID |

已选择 QQ 邮箱 SMTP 真实发送，连接配置统一放在 `application.yml`。设置 `SMTP_USERNAME` 和 `SMTP_PASSWORD`（QQ 邮箱授权码），然后实现 `sendCode` 的邮箱规范化、随机验证码、Redis 存储、有效期、发送冷却和邮件发送逻辑。真实发送时不要回显 `devCode`。`login` 也仍需实现，并沿用相同的邮箱规范化和 Redis Key。

新注册用户只能是 USER；管理员使用预置数据。并发首次登录同一邮箱时，应复用唯一账号，不创建重复用户。

### 3. 双拦截器（已实现，MVC 注册待手写）

- 请求头使用 `authorization: <token>`，直接传登录返回的 token。
- `RefreshTokenInterceptor` 从 Redis 读取登录态，保存到 `UserHolder` 并刷新 TTL；没有登录态也放行。
- `LoginInterceptor` 对需要登录的接口检查 `UserHolder`，未登录返回 401。
- 管理端校验 ADMIN 权限；考虑角色变更后权限何时失效。
- 请求结束清理上下文，不让线程复用串号。
- 缺失、格式错误、过期和退出后的 Token 都要有明确结果。

在 `WebMvcConfiguration.addInterceptors` 中手写注册两个拦截器，让刷新拦截器先执行、登录拦截器后执行。注册时需从登录拦截范围中排除 `/user/auth/code`、`/user/auth/login` 和接口文档路径；注册完成后直接生效，无需额外开关。登录态 TTL 统一在 `RedisKeyConstant` 中设置。

### 4. 对应接口

`POST /user/auth/code`、`POST /user/auth/login`、`POST /user/auth/logout`、`GET /user/auth/me`。

### 验收

- 正确验证码可以登录；过期、错误、重复使用均不能登录。
- 连续错误尝试和高频发送受到限制。
- Token 有 TTL，Hash 创建与 TTL 设置的失败窗口得到处理。
- 普通用户访问 `/admin/**` 返回 403；退出后 Token 无效。
- 验证码和完整 Token 不出现在正常业务日志中。

## 第二阶段：站点缓存与分布式锁

> 难度：★★★☆☆｜涉及：布隆过滤器、空值缓存、逻辑过期、Redisson、缓存一致性。

当前 `GET /user/stations/{id}` 已接通 `StationService.detail`，启用布隆过滤器、空值缓存和逻辑过期缓存。此阶段只查询详情，不记录访问或 UV，也不依赖 `StatisticsService`。

### 已实现的缓存穿透防护

查询顺序：站点缓存 → 布隆过滤器 → 加锁后二次检查缓存 → 数据库。

- 缓存命中正常数据：沿用逻辑过期及异步重建；命中空字符串：直接返回 404。
- 缓存未命中且布隆明确不存在：直接返回 404，不查询数据库，也不为随机无效 ID 批量写空缓存。
- 布隆判断可能存在：在原有站点互斥锁内回源；数据库确实不存在时，写入空字符串，TTL 为 180～240 秒。
- 布隆未完成加载、初始化失败或布隆操作异常时，放行到原有回源路径，不能把异常当作“不存在”。
  此降级只针对布隆；缓存 Redis 或回源锁整体不可用时，仍按现有异常处理返回错误。
- 异步重建发现站点已删除，也写入短期空值缓存。

`StationBloomFilter` 使用 Redisson `RBloomFilter<String>`，以十进制站点 ID 字符串入库。
启动时按 ID 游标、每批 1000 条加载已存在的站点；只有全部加载完成才写入共享就绪标记。
查询发现就绪标记或位图丢失时会尝试重新加载，加载期间或等待锁超时的查询允许回源。
过滤器与就绪标记均不设置 TTL；需与业务数据库配套维护，不能恢复为不完整的旧快照。

管理端新增站点先取得布隆构建锁，写数据库并在提交前添加 ID，锁保持到事务结束。
布隆写入失败则数据库事务回滚；回滚留下的布隆位只是可由空值缓存处理的误判。
新增/修改/删除仍在提交后使用站点互斥锁删除详情缓存，因此先前的空值缓存也会被清理。
若缓存失效失败，空值最多保留到 TTL 到期。删除站点不删除布隆位，避免影响其他 ID。

配置位于 `application.yml`：

```yaml
epic:
  station-bloom:
    expected-insertions: ${STATION_BLOOM_EXPECTED_INSERTIONS:100000}
    false-probability: ${STATION_BLOOM_FALSE_PROBABILITY:0.01}
```

容量必须大于 0，目标误判率必须在 0 和 1 之间。容量应覆盖累计写入的站点 ID（含已删除站点）。
这些参数用于首次初始化，修改配置不会自动调整已经存在的位图；需要扩容时应协调所有实例，
使用新版本的布隆及就绪 key 完整加载后再使用，不能直接清除某些布隆位。
当前启动加载采用追加方式，不清除删除站点留下的位，长期积累会增加误判率。

正常新增必须走管理端业务。直接通过 SQL 导入站点后，应在恢复流量前使旧就绪标记失效并
重新启动应用完成全量加载；仅写数据库不会自动同步过滤器。Redisson 与 Spring Redis 必须连接同一 Redis 数据库。

相关测试使用 H2、真实 Service/Mapper/事务与模拟 Redis/Redisson，覆盖历史数据分批加载、
负向拦截、误判空值缓存、空缓存到期、过滤器故障与位图丢失、新增/删除/回滚以及并发构建。

### 开发入口

- `LockHelper.withLock(String key,Supplier<T> action)`。
- `StationServiceImpl.detail/save/delete`。
- `RedisKeyConstant.station(id)`，当前前缀为 `gc:cache:station:`。

### 逐步完成

1. 保留数据库查询作为回源路径，加入缓存命中逻辑。
2. 区分“缓存未加载”与“站点不存在”，处理缓存穿透。
3. 对热点 Key 的并发重建进行互斥控制，防止击穿。
4. 使大量 Key 的过期时间错开，降低雪崩风险。
5. 修改/删除数据库成功后维护缓存，考虑事务回滚时的行为。

本阶段的重点不是简单地写出 GET/SET，而是解释：更新、删除、读请求重建同时发生时，旧数据能否再次进入缓存，最长会保留多久。

### 必须思考

- 未获得锁的请求怎么办，是否有界等待？
- 业务异常时是否释放自己持有的锁？
- 数据库提交成功、缓存删除失败，如何收敛？
- 锁过期、线程阻塞或实例退出会有什么影响？
- 缓存是否可以作为预约容量的最终判断来源？

### 验收

- 重复查不存在站点不会每次都访问数据库。
- 热点缓存失效时，不出现所有请求同时回源。
- 更新/删除后缓存按设计收敛，回滚不会留下假数据。
- 预约的严格业务判断仍有数据库保护。

## 第三阶段：附近充电站查询（GEO）

## 第四阶段：预约唯一 ID 与重复预约控制（Snowflake、Set）

> 难度：★★★☆☆｜涉及：雪花算法、ID 唯一性、Set、幂等语义。

### 开发入口

- `SnowflakeIdWorker.nextId()`。
- `ReservationServiceImpl.submit(userId,dto,synchronous)` 中的 ID 生成与重复预约检查。
- 现有 `ReservationMapper.findRequest/activeForUser/insert` 等数据库方法，作为校验与持久化支持。

### 1. 唯一订单 ID

订单 ID 已使用 Hutool 雪花算法，由 Spring 单例 `SnowflakeIdWorker` 统一生成，发号不依赖 Redis。
结构为符号位 1 位、毫秒时间差 41 位、数据中心 5 位、机器编号 5 位、毫秒内序列 12 位，
使用 Hutool 默认纪元 `1288834974657`（毫秒），不要在上线后修改纪元。

`application.yml` 的 `epic.id.worker-id` 和 `epic.id.datacenter-id` 分别通过
`SNOWFLAKE_WORKER_ID`、`SNOWFLAKE_DATACENTER_ID` 环境变量设置，范围均为 0～31；非法值启动失败。
默认 `(0,0)` 仅适用于单实例；共享订单库的实例必须使用不同编号组合，包括滚动发布时并存的实例。
同一实例各业务共用此发号器，不再按业务前缀建立 Redis 计数器。

运行中发现时钟回拨会抛出异常、停止本次发号，时钟恢复后可重试；毫秒内序列耗尽会等待下一毫秒。
发号器不持久化最后时间戳，因此跨进程重启不能检测此前的时钟回拨；重用编号前需确保时钟已超过
该编号上次发号时间，且旧实例已停止。不能仅依靠默认编号保证多实例全局唯一。

数据库继续存储 `BIGINT`，历史订单无需改号；预约响应中的 `id` 改为字符串，避免 JavaScript 精度丢失。
前端应原样保存和传递该字符串，不要用 `Number` 或 `parseInt` 转换。MQ 已使用字符串传递订单 ID。
`requestId` 仍由客户端生成，用于请求幂等；登录 token 保持随机生成。

### 2. 区分两种“重复”

| 情况 | 业务语义 |
| --- | --- |
| 同用户、同 requestId、同 slotId | 同一次请求重试，应返回原订单 |
| 同用户、同 requestId、不同 slotId | 请求标识被错误复用，应拒绝 |
| 同用户、不同 requestId、同 slotId，已有活动订单 | 重复预约，应拒绝 |
| 原订单取消/失败后，使用新 requestId | 新预约，可重新校验名额 |

使用 Redis Set 承载时段活动用户关系，并思考它与订单 ID、请求 ID 各自承担什么职责。数据库唯一索引是已提供的最终防线，不需要重写。

### 3. 为下一阶段准备

单独使用 Set 做资格检查还不等于并发安全。先在 Java 判断未预约，再分别扣减名额和添加用户，仍然存在竞争窗口。

本阶段明确数据模型与幂等语义；下一阶段通过 Lua 将必须共同生效的操作纳入原子执行。不要把尚未原子化的临时实现当作最终并发方案。

### 验收

- 并发生成大量 ID，没有重复和越界。
- 已取消订单的 requestId 重试返回原订单，不偷偷新建订单。
- Set 丢失时不会绕过已有数据库唯一约束。
- 能解释为何“先判断，再写入”的多条 Redis 命令不足以防重复预约。

## 第五阶段：Lua 原子预占与异步预约入口

> 难度：★★★★☆｜涉及：Set 判重、Lua、名额预占、Script 加载。

### 开发入口

- `ReservationServiceImpl.submit(userId,dto,false)`。
- `Scripts.load(String name)`、`resources/lua/`。
- `POST /user/reservations`。

### 需要自己定义的内容

1. 名额、活动用户、预占归属、请求幂等等 Redis 数据结构。
2. Key 初始化来源、生命周期和恢复条件。
3. 脚本参数、返回码以及对应的业务含义。
4. MySQL PROCESSING 订单与 Redis 预占的先后关系。
5. 预占结果如何交给后续 Stream 消费者。

脚本应把必须一起生效的校验和状态变更放在同一次原子执行中，而不是在 Java 中分几次读写后假设没有并发。

### 关键边界

- 区分名额 Key 缺失、名额为零、用户已有预约、同一订单重试。
- 明确预占是否占用 MySQL `reserved`；本项目建议 `reserved` 只统计 SUCCESS，PROCESSING 单独参与 Redis 预占。
- 数据库可能已经提交而响应丢失，客户端需要使用原 requestId 重试。
- 64 位订单 ID 在 Lua 中应作为字符串保留，避免不必要的数值转换。
- Lua 的原子执行不等于脚本报错时自动回滚已发生的写入，需要考虑错误类型和部分执行失败。

### 本阶段验收

- 并发预占不会扣成负数。
- 重复请求不重复扣名额。
- 未初始化 Key 不会被当作无限容量。
- 请求返回 PROCESSING 时，客户端能查到该请求对应的订单/处理结果。
- Redis 数据丢失时不会绕过数据库唯一约束和容量保护。

## 第六阶段：Stream 异步消费、确认与重试

> 难度：★★★★★｜涉及：消费者组、PEL、接管、事务幂等、后台生命周期。

### 开发入口

- `ReservationStreamConsumer.poll()`。
- `ReservationServiceImpl.consume(Long id)`。
- `RedisKeyConstant.STREAM`：`gc:{reservation}:stream`。
- `RedisKeyConstant.GROUP`：`reservation-workers`。

任务类目前不是 Spring Bean，也没有调度。实现核心逻辑、异常处理和停止方式后，再决定使用调度器还是受管理线程运行；不要直接开启一个只会抛待实现异常的任务。

### 开发内容

- 消费者组初始化：处理首次创建、重复启动和多实例竞争。
- 消息结构：至少能定位订单；不盲目信任消息中的所有业务字段。
- 消费逻辑：读取数据库当前状态，执行事务内条件扣减及状态转换。
- 消费确认：只在需要的数据库事务和补偿步骤完成后 ACK。
- 失败重试：处理当前消费者及已经退出消费者遗留的 pending。
- 毒消息处理：一条坏消息不能让整个消费者无限忙循环。
- 生命周期：可停止、异常有日志、实例重启后能继续处理。

### 必须回答的问题

| 问题 | 应达到的结果 |
| --- | --- |
| 数据库提交成功、ACK 前宕机 | 再次消费不重复扣名额 |
| 数据库事务失败 | 消息不能当作成功处理丢弃 |
| 消费者 A 退出，B 启动 | B 能接管 A 的待处理消息 |
| Stream 写入前后发生中断 | 已受理请求仍能查询或恢复 |
| 消息非法或对应订单缺失 | 有界重试/隔离，不阻塞正常消息 |
| 同一消息重复进入队列 | 最终状态和计数保持一致 |

### 验收

正常提交后可从 PROCESSING 进入终态；重复消息不重复扣减；重启消费者可以恢复积压；关闭数据库时不会把失败工作 ACK 掉。不要仅测试正常 `XREADGROUP` 路径。

## 第七阶段：取消预约、名额释放与最终一致性

> 难度：★★★★★｜涉及：并发状态机、补偿、持久化恢复来源。

### 开发入口

- `ReservationServiceImpl.cancel(userId,id)`。
- `ReservationServiceImpl.recover()`。
- `RecoveryTask.recover()`。
- `POST /user/reservations/{id}/cancel`。
- `SlotMapper.recoveryIds(after)`、`ReservationMapper.active(slotId)`。

### 取消规则

- 只能取消自己的订单；时段开始后拒绝取消。
- SUCCESS 取消需要释放已成功名额。
- PROCESSING 取消不能误减尚未增加的 MySQL `reserved`。
- 重复取消同一订单，不重复释放。
- FAILED 订单无需再释放成功名额，应返回明确业务结果。
- 取消与消息消费同时执行，不能出现 CANCELLED 最终又变为 SUCCESS。
- 用户取消后重新预约，旧消息不能释放新订单持有的名额。

### 恢复设计

在不新增业务表的前提下，说明如何利用现有订单状态作为恢复来源。不要把尚未落库的请求只存在 Redis，却又假设 Redis 丢失后能够完整重建。

需要覆盖：

1. 数据库取消成功，Redis 释放失败。
2. Lua 预占成功，进程在后续步骤前退出。
3. PROCESSING 长时间没有进入终态。
4. Redis 的名额、用户集合或 Stream 丢失。
5. 恢复任务与新预约、消费、取消并发执行。

`recoveryIds` 已提供每批 100 个时段 ID 的查询，你需要维护游标，并为单个时段的失败设置重试方式，避免一个异常阻止全部恢复。

### 验收

稳定状态下至少满足：

```text
数据库 reserved = 同时段 SUCCESS 订单数
数据库 reserved 不为负，也不大于 quota
没有遗留 PROCESSING 时：Redis 可用名额 = quota - reserved
```

存在 PROCESSING 时，需要按你定义的有效预占规则核对，不能机械地用 `quota - reserved` 覆盖 Redis，从而释放其他请求仍持有的预占。

## 第八阶段：站点关注与共同关注（Set）

> 难度：★★★☆☆｜涉及：数据库与 Set 同步、集合交集。
> 完成登录后即可提前练习本阶段，不强制依赖高并发预约完成。

### 复用现有数据库底座

`FollowServiceImpl.follow(userId,stationId,enabled)` 已有数据库插入/删除；`list(userId)` 已有数据库列表。
`common(userId,otherId)` 待实现，已有 CRUD 还没有维护 Redis Set。

### 对应接口

| 接口 | 对应方法 |

## 第九阶段：站点动态与滚动分页（Feed）

> 难度：★★★★☆｜涉及：ZSet、关注时间、分页游标、推送恢复。

### 开发入口

- `FollowServiceImpl.publish(StationSlot slot)`。
- `FollowServiceImpl.feed(userId,max,offset,size)`。
- `StationServiceImpl.publish(stationId,dto)`：新增“时段提交成功后发布动态”的衔接。
- `FollowMapper.followers(stationId)`、`FollowMapper.feed(userId)`。
- `GET /user/follows/feed`，返回 `FeedVO(records,nextMax,nextOffset)`。

### 业务规则

- 动态代表“站点发布了新的预约时段”，不增加动态业务表。
- 使用已落库的时段 ID 标识动态，时间语义在推送与恢复时保持一致。
- 新增时段事务失败，不发送假动态。
- 发布成功但推送失败，允许后续恢复，不能永久丢失动态。
- 当前数据库回填 SQL 仅包含关注之后发布的时段，最近 30 天、最多 1000 条。
- 按这个口径，取关后不再展示该站动态；重新关注后，旧动态是否可见必须与关注时间过滤保持一致。

### 分页规则

首次使用接口默认值：`max=Long.MAX_VALUE,offset=0`，后续传回上次返回的 `nextMax/nextOffset`。
不要直接改成普通 page/size；重点解决多个动态时间分数相同的情况。

### 验收

- 连续插入时间分数相同的动态，多页查询不重复、不遗漏。
- 翻页期间出现新动态，不破坏已有游标的约定。
- 发布重试不会产生重复动态。
- Redis 收件箱丢失后可以按已定义范围回填。
- 空页面有明确结束语义，客户端不会无限请求同一页。

## 第十阶段：运营统计（Bitmap、HyperLogLog、ZSet）

> 难度：★★★☆☆～★★★★☆｜涉及：统计口径、去重、缓存与聚合。

### 1. 每日活跃与连续活跃天数

开发 `StatisticsServiceImpl.markActive(userId)` 与 `streak(userId)`。

- 定义“活跃”为已登录用户当天发生有效访问。
- 按日期映射位图位置，按月组织时要处理跨月连续天数。
- 在登录鉴权成功后的合适位置记录；不要让未登录请求替别人标记。
- `GET /user/activity/streak` 返回截至今天的连续活跃天数，现有摘要约定最多 366 天。
- 同一天重复访问只记录一次；中断一天、月末/月初均要测试。

### 2. 站点每日 UV

开发 `visit(stationId,userId)` 与 `uv(stationId,date)`。

- 学到本阶段时，再为用户端站点详情接口接入 `StatisticsService.visit`，在查询真实存在的站点详情后记录访问；前面的缓存阶段不接入统计。
- 按“站点 + 日期”分组，以当前用户 ID 去重。
- 使用 HyperLogLog，明确结果为近似独立访客数，不是访问次数。
- `GET /admin/statistics/stations/{id}/uv?date=YYYY-MM-DD` 查询。
- 沿用接口摘要，建议保留 90 天；旧数据缺失时结果如何表达需保持一致。
- 同一用户访问十次不按十人计；不同站点、不同日期分别统计。

### 3. 热门预约排行榜

开发 `ranking(LocalDate date,int size)`，接通 `GET /admin/statistics/ranking`。

当前 Mapper 已提供按订单创建日统计仍为 SUCCESS 的订单数：`ReservationMapper.ranking(start,end)`。
返回 `RankingVO(stationId,stationName,reservations)`。

- 使用 ZSet 保存/查询排行，按预约数量降序展示。
- 口径是“某创建日的当前有效成功预约”，不是充电时段当天的订单，也不是历史累计预约。
- 取消后有效数量应减少；重复消费不能把排行重复加分。
- 可自行选择增量维护或数据库聚合后重建，但需说明一致性和恢复方式。
- 沿用接口摘要，目标刷新延迟不超过 30 秒；并列名次的排序约定应明确。

### 统计数据恢复边界

预约排行能从现有订单恢复，关注/Feed 有数据库来源；活跃和 UV 没有对应的完整访问明细表。
不要声称 Redis 数据丢失后所有统计都可以由五张表恢复，应明确保留策略和可接受的数据损失范围。

## 第十一阶段：Redis 业务联调、并发测试与故障演练

> 难度：★★★★★｜目标：用测试证明业务规则，不只证明接口能返回 200。

### 1. 测试账号与基础数据

演示数据提供 `admin@gridcharge.local`、`driver@gridcharge.local`、`friend@gridcharge.local`。
这些是邮箱验证码登录账号，没有固定登录密码。QQ 邮箱 SMTP 连接配置已准备，需配置发件账号和授权码；发送验证码和登录校验仍需在第一阶段自行实现。
示例时段基于首次导入日期生成；过期后通过管理接口发布新时段。

### 2. 分阶段验收清单

| 类别 | 必测场景 |
| --- | --- |
| 鉴权 | 无 Token、错误/过期 Token、退出、普通用户访问管理端 |
| 缓存 | 空值、过期并发回源、更新与重建竞争、删除失败 |
| GEO | 经纬度/距离单位、站点停用、坐标修改、索引丢失 |
| 预约 | 超额竞争、同请求重试、同用户不同请求、事务回滚 |
| Stream | 重复投递、ACK 前后中断、其他消费者 PEL、坏消息 |
| 取消 | 重复取消、处理中取消、取消与消费竞争、旧消息迟到 |
| 恢复 | Redis 预占丢失、Stream 丢失、数据库短暂不可用 |
| Feed | 相同时间分数、分页中新动态、回填、取关/重新关注 |
| 统计 | 重复访问、跨月活跃、取消后的排行、重复消费不多计 |

### 3. 测试组织建议

- 围绕 Redis 功能测试：先验证数据结构与脚本，再验证 Redis/MySQL 协调，最后做真实 HTTP、并发和故障联调。已有 CRUD 仅作为测试数据准备手段。
- 并发测试使用不同用户或不同请求标识，检查最终数据库记录，而不只统计 HTTP 成功数。
- 新增真实 Redis 测试时使用隔离前缀，结束后只清理自己的 Key。
- 检查事务是否真正生效，避免同类方法自调用导致注解没有经过代理。
- 现有 `ScaffoldContextTest.controllerReturnsEmptyResponse` 是骨架约束；接通接口后应更新为真实业务断言。
- 现有“不启动 Redisson/任务”的测试也要随配置设计调整，不能为了保持旧测试而阻止功能接入。

### 4. 完成标准

- Redis 相关入口接通，并能从接口观察到正确的业务结果；基础 CRUD 不作为阶段成果重复考核。
- 已接入路径不存在待实现异常；Redis 工具和任务有对应测试。
- 不超额、不重复、不越权，取消和重复消息不能破坏状态机。
- Redis/MySQL 不一致有明确恢复机制和可观测日志。
- README 更新实际启用的开关、连接方式、运行步骤及尚未验证的限制。

## 附录 B：每完成一个 Redis 阶段的自检问题

1. 当前用户从哪里来，有没有相信客户端传来的他人身份？
2. MySQL 中哪些变化必须处于同一个事务？
3. 重复调用或重复消息会不会重复写入、扣减、释放？
4. 数据库已成功，但 Redis 失败，用户会看到什么，后台如何修复？
5. 进程在任意一步退出，已受理请求是否仍有可恢复来源？
6. 并发测试检查的是实际业务数据，还是只检查接口没有报错？

建议先独立完成每一个 Redis 阶段，再与原 GridCharge 对照复盘。文档中的规则是验收目标，具体类拆分、事务实现和 Redis 脚本由你自己完成。
