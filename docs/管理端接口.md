# 管理员登录与站点管理

管理员账号沿用 `db/data.sql` 中的 `admin@gridcharge.local`，数据库角色必须是 `ADMIN`。
先执行项目的 schema.sql 和 data.sql 初始化数据库。管理员登录只提交密码；
必须通过环境变量 `ADMIN_PASSWORD` 设置密码，未配置时无法登录；通过 `ADMIN_EMAIL` 选择数据库中已有的管理员账号。
登录操作不会创建管理员或将普通用户提升为管理员，也不需要修改数据库表结构。

## 登录和权限

```http
POST /admin/auth/login
Content-Type: application/json

{"password":"填写你设置的管理员密码"}
```

成功返回 `{"code":1,"msg":null,"data":"生成的token"}`。
后续请求在 `authorization` 请求头中直接填写 token，不加 `Bearer ` 前缀。
登录态复用 Redis Hash 和滑动续期逻辑；客户端不能指定角色。

除 `/admin/auth/login` 外，所有 `/admin/**` 接口均要求管理员身份：

- 未登录、无效或过期 token：HTTP 401。
- 普通用户、角色缺失，或数据库中管理员角色已撤销：HTTP 403。
- 密码错误：HTTP 401；管理员账号不存在或已不是 ADMIN：HTTP 403。
- 管理员账号不通过用户邮箱验证码接口登录，应使用管理端密码登录。

## 退出登录

```http
POST /admin/auth/logout
authorization: <管理员 token>
```

无需请求体，成功返回 `{"code":1,"msg":null,"data":null}`。
删除当前 token 对应的 Redis 会话并清理当前线程用户信息；其他设备的会话不受影响。
登出后该 token 访问受保护接口或再次登出均返回 401；普通用户调用管理端登出返回 403。
前端应同步清除本地 token 并跳转登录页。Redis 删除失败会返回错误，不会返回登出成功。
已经通过鉴权的在途请求不会因本次登出被撤回。

用户端使用 `POST /user/auth/logout`，携带用户 token，处理方式相同。

## 站点接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/admin/stations?page=1&size=10&name=大学城` | 分页、按名称模糊查询；name 可省略 |
| GET | `/admin/stations/{id}` | 数据库中的最新站点详情 |
| POST | `/admin/stations` | 新增站点，返回站点 ID |
| PUT | `/admin/stations/{id}` | 完整修改站点，包含启用/停用状态，返回站点 ID |
| DELETE | `/admin/stations/{id}` | 删除无预约时段关联的站点 |

新增与修改使用相同的请求体，所有字段均必填：

```json
{
  "name": "大学城充电站",
  "address": "福州市闽侯县大学城",
  "longitude": 119.198000,
  "latitude": 26.058000,
  "maxPowerKw": 480,
  "pileCount": 8,
  "status": 1
}
```

`status` 为 1 表示启用、0 表示停用；`page` 为 1～100000，`size` 为 1～100。
分页结果位于 `data.total` 与 `data.records`。
非法参数返回 400，站点不存在返回 404。
降低容量导致已有未结束时段无法被承载，或删除存在时段的站点，返回 409。

站点新增、修改和删除在数据库事务提交后清除站点缓存；事务回滚不清除缓存。
新增站点在提交前同步布隆过滤器，同步失败则回滚新增；与全量构建共用布隆锁直到事务结束。
删除站点保留布隆位，用户查询数据库确实不存在时使用 180～240 秒的空值缓存。
清除缓存与用户端缓存重建共用站点锁，用户端缓存缺失时加锁回源。
缓存服务异常时记录日志，已提交的数据库变更不回滚，旧缓存依靠逻辑过期后重建恢复。

## 预约时段管理

以下接口均需要管理员 token：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/admin/stations/{id}/slots` | 发布时段，返回时段 ID |
| POST | `/admin/stations/slots/{slotId}/close` | 停止接收新预约，保留已有成功预约 |
| POST | `/admin/stations/slots/{slotId}/open` | 维修完成后重新开放尚未开始的时段 |
| POST | `/admin/stations/slots/{slotId}/cancel` | 关闭时段并取消其中的有效预约，返回本次取消订单数 |

发布请求体示例（时间应换成未来时间）：

```json
{
  "startTime": "2027-01-01T14:00:00",
  "endTime": "2027-01-01T15:00:00",
  "quota": 8,
  "powerPerCarKw": 30,
  "price": 1.50
}
```

开始时间必须在未来，结束时间必须晚于开始时间；名额不能超过充电桩数量和
`floor(站点总功率 / 单车预留功率)` 两者的较小值。站点必须启用，同站点时段不能重叠，
允许前一时段结束时间等于后一时段开始时间。关闭的时段仍参与重叠检查，不会被删除。
参数或容量不合法返回 400，站点/时段不存在返回 404，站点停用或时段重叠返回 409。
关注 Feed 推送仍是独立待实现功能，发布接口目前只创建时段。

关闭和取消无需请求体，均可重复调用。关闭返回 `{"code":1,"msg":null,"data":null}`；
取消返回 `{"code":1,"msg":null,"data":2}`，其中 2 是本次从 `SUCCESS` 或 `PROCESSING`
转为 `CANCELLED` 的订单总数，重复取消返回 0。取消原因记录为“管理员取消该时段预约”。
已有 `FAILED`、`CANCELLED` 订单保持原状；其他时段不受影响。

仅关闭时，`SUCCESS` 订单和占用名额保留，`PROCESSING` 订单由消费者处理为失败。
取消时段时，关闭入口、取消有效订单和将 `reserved` 清零在同一数据库事务内完成；
任何一步失败都会回滚。也支持先关闭，随后取消。当前订单模型没有已履约状态，接口未限制
时段是否已开始或结束；调用取消即撤销该时段所有仍处于上述有效状态的订单。
取消会为本次被取消的订单生成邮件通知任务；不包含支付或退款流程。

维修完成后调用重新开放接口，无需请求体：

```http
POST /admin/stations/slots/1/open
authorization: <管理员 token>
```

成功返回 `{"code":1,"msg":null,"data":null}`，将时段 `status` 设为 `1`。
要求站点启用、时段尚未开始；满足条件的已开放时段重复调用也成功。
时段 ID 非正数返回 400，不存在返回 404；站点停用、时段已开始或已结束返回 409。
已开始或结束的时段应重新发布未来时段。
开放操作仅修改时段状态，保留 `reserved`、所有订单状态及原取消邮件任务，不发送恢复通知。
之前已取消的预约不会恢复，用户需使用新的 `requestId` 重新预约；旧 `requestId` 仍返回原订单。

管理端使用 Redisson 的 `RLock`：发布、修改和删除站点共用
`gc:lock:admin:station:{stationId}`；关闭/取消/重新开放按顺序取得站点锁和
`gc:lock:admin:slot:{slotId}`。最多等待 5 秒，不指定固定 leaseTime，由 watchdog 续期。
获取失败返回 503，不继续写库。锁通过 Spring `afterCompletion` 回调在提交或回滚后释放，
提交前会检查锁所有权。数据库事务和条件更新继续保留。

用户端业务保持原样：预约提交、消费仍使用 MySQL 时段行锁。因此管理端关闭/取消/重新开放仍保留
`slotMapper.lockById`，用于与用户端协调；只换成 Redis 锁无法和现有用户端行锁互斥。
管理端不再主动锁定站点数据库行，但 SQL 写操作仍会产生数据库自身的锁。
发布先取得站点 Redis 锁，再检查冲突并插入；所有应用实例必须使用相同 Redis 和锁 key。
此改动仅覆盖管理端，不改变用户端预约和消息消费流程。

Redis 锁的互斥依赖锁服务可用及持有期间所有权有效，不能视为与数据库锁故障语义完全相同；
watchdog 及提交前检查不能完全排除长暂停、网络分区造成的锁丢失风险。

## 取消预约邮件通知

调用 `/admin/stations/slots/{slotId}/cancel` 时，在取消事务中为本次有效订单保存邮件任务。
收件人使用预约用户在 `tb_user.email` 中的邮箱，邮件包含预约编号、站点、起止时间和取消原因。
原状态为 `PROCESSING` 时，正文说明“预约申请已取消”，不宣称此前预约成功。
仅关闭时段不发送取消邮件；重复取消不会重复创建任务。取消接口的返回值仍然是本次取消订单数，
表示取消及通知任务已提交，不表示邮件已经送达。

已有数据库必须先执行升级脚本（仅新增通知表，不修改原有业务表）：

```sql
USE epic_learning;
SOURCE D:/Epic/src/main/resources/db/migrations/20261025_admin_cancellation_mail.sql;
```

新数据库执行 `schema.sql` 已包含该表。应用不会自动执行数据库迁移。
通知入库失败会回滚整个取消事务，避免取消成功但没有可恢复的通知记录。

复用现有 `spring.mail` 配置及 `JavaMailSender`，配置 `SMTP_USERNAME` 和 `SMTP_PASSWORD`
（邮箱 SMTP 授权码），不修改用户端登录、预约提交、查询或消费逻辑。
后台任务默认启用，每轮结束后等待 10 秒再扫描，每轮最多处理 20 封；启动后首次等待 10 秒。
可用 `ADMIN_CANCELLATION_MAIL_POLL_MS` 调整间隔；`ADMIN_CANCELLATION_MAIL_ENABLED=false`
暂停发送，但仍保存取消时产生的任务，恢复启用后继续发送。

取消事务提交后，独立后台任务才能读取并发送邮件。SMTP 操作不占用取消事务或业务锁。
任务按预约编号使用 Redisson 锁，拿锁后重新检查状态，协调多实例并发发送。
发送失败保持 `PENDING`，按 1、2、4、8、16、32、60 分钟退避，随后以一小时间隔持续重试；
应用重启后未完成任务仍保留。SMTP 接受后标记 `SENT`，并记录发送时间。

可查询待发任务排查配置和发送情况：

```sql
SELECT reservation_id,status,attempts,next_attempt_at,last_error,sent_at
FROM tb_admin_cancellation_mail
ORDER BY create_time DESC;
```

`last_error` 仅记录异常类型，不保存 SMTP 凭据、响应详情或邮件正文。
SMTP 接受邮件不等于用户已读或必然进入收件箱；如果 SMTP 已接收但保存 `SENT` 前进程崩溃，
或者发送超时而实际已送达，后续重试可能重复发信。本实现采用持久化重试，不能承诺严格只投递一次。
历史上已取消的订单不会自动补发通知。

## 测试

使用 JDK 17：

```powershell
$env:JAVA_HOME = 'D:\develop\JDK-17'
mvn -o '-Dtest=AdminManagementTest,ReservationConsumeTest,ReservationSubmitFlowTest' test
```

管理员测试使用真实 MVC 配置、拦截器、Service、MyBatis 和 H2 事务，模拟 Redis/Redisson；
不依赖运行中的 MySQL、Redis 或 RocketMQ，也不修改本地业务数据。
时段测试覆盖接口权限、参数校验、容量/时间冲突、关闭保留预约、取消幂等、迟到消息、
重新开放幂等及状态校验、取消后重新预约、开放与取消并发、开放事务回滚、
事务回滚，以及并发发布、取消与提交/消费的两种执行顺序。管理端 RLock 用按 key 的本地可重入锁
模拟互斥，并覆盖事务完成后解锁、获取超时及提交前锁失效。H2 和模拟锁测试不替代 MySQL/Redis 实环境验证。
邮件测试使用真实任务表和 Mapper、模拟邮件发送器，覆盖提交前不发信、回滚不留任务、
仅通知受影响订单、邮箱快照、重试退避及并发发送互斥；测试不会发送真实邮件。
